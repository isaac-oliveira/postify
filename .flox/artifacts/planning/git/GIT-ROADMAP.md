# Roteiro de Git — Postify

## Estratégia e branches

`main` representa produção e `develop` representa a próxima versão. O
desenvolvimento comum começa em `develop` e usa branches `feature/*`, `fix/*`,
`chore/*`, `refactor/*` e `test/*`. Releases usam `release/*` e hotfixes usam
`hotfix/*`.

O fluxo comum é `develop` → branch de trabalho → PR → `develop`. Releases
partem de `develop` e chegam a `main`; hotfixes partem de `main`, chegam a
`main` e também são incorporados em `develop`.

## Regras de merge e finalização

Todo merge ocorre por PR com os checks obrigatórios aprovados. Não deixar
`main` e `develop` divergirem após releases ou hotfixes.

Commits usam Conventional Commits, com mensagem curta, sem descrição longa,
sem co-author e com uma mudança lógica por commit.

### Handoff dev-story → code review → merge humano

1. **Ao finalizar o `flox-dev-story`**: criar os commits de forma atômica
   (Conventional Commits, uma mudança lógica por commit), dar push na branch de
   trabalho e abrir o PR para `develop`, deixando pronto para o code review.
2. **Após a aprovação do `flox-code-review`**: o fluxo automatizado para e não
   faz merge automático. Registrar/avisar que está aguardando o review humano
   final e o merge manual do PR por Isaac.
3. **Quando Isaac faz o merge do PR**: o agente faz checkout na `develop`,
   atualiza (pull) a develop local e apaga a branch de trabalho (local; a
   remota é excluída pelo auto-delete do GitHub).

Isaac é responsável por manter a estratégia e aprovar o resultado. O resultado
aprovado é `approve`. Merge direto sem PR, merge automático pelo agente, checks
obrigatórios falhando ou branch de release/hotfix não sincronizada bloqueia a
aprovação.
